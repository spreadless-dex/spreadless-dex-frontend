With more than one vault, the same pair can be traded along more than one path.
Spreadless splits that problem in two: an **off-chain pathfinder** that finds and
prices candidate routes in the browser, and an **on-chain Router** that executes
the chosen route as a single Soroban transaction.

<Callout kind="note" title="Status">
  The pathfinder, the swap UI and the Router are all live on testnet. One
  contract does both jobs: it deploys and registers pools, and it executes
  multi-hop swaps across the pools it registered. A route can only cross pools
  it created, so the pre-Router pool is a single hop and never a leg. The swap
  page also includes a routing demo with two local vaults, where the full flow
  including the atomic rollback runs without signing anything.
</Callout>

## The pathfinder

1. **Read the registry.** The set of vaults is the Router's registry, walked
   from `next_pool_id()` and `pool_at(id)`, plus the pool that predates it.
2. **Build the graph.** Tokens are nodes, vaults are edges, keyed by contract id.
   Symbols are display labels only and never take part in the search.
3. **Enumerate candidates.** A bounded depth-first search with a maximum of
   three hops. A token never repeats along a route, and neither does a vault:
   routing through the same pool twice moves its reserves against you on the
   second leg, so the search never proposes it. The contract does not forbid it,
   which is exactly why the pathfinder does.
4. **Quote every candidate.** Each leg is simulated against the vault that holds
   the pair, feeding one leg's output into the next. Results stream into the
   graph as they land, so a fast route never waits behind a slow one.
5. **Pick the best.** The route with the highest final output wins. The others
   stay on screen with their shortfall in basis points, so the choice is
   auditable, not asserted.

Only the final output is protected. Intermediate amounts are simulations and
are shown as such.

## The Router

A multi-hop swap is one call:

```ts
swap_exact_in({
  to,         // signer, payer of token_in, and recipient of the output
  token_in,   // address of the token being sold
  path,       // [{ pool_id, token_out }, ...], one entry per leg
  amount_in,  // bigint, raw units of token_in
  min_out,    // bigint, floor on the FINAL output
}) // -> bigint  (last token_out received)
```

A leg names a **pool id**, the number the Router handed out when it created the
pool, and never a contract address. Only pools it created have one, so a pool
deployed any other way can be swapped against directly but can never be a leg of
a route. The app refuses such a route before asking for a signature rather than
letting it simulate into `PoolNotRegistered`.

A leg carries no `token_in` of its own either: what it sells is the previous
leg's output, or `token_in` for the first. Token continuity is therefore a
property of the call, not something to be checked.

Inside that one call the Router:

- takes the input token from `to` under that address's authorization,
- executes each leg in order, holding the intermediate token itself,
- transfers the final output back to `to`,
- enforces `min_out` on that final amount.

If any of those steps fails, the whole invocation reverts. There is no state in
which the user holds an intermediate token they did not ask for.

## What the interface shows

- **Route graph.** Source and destination once, every candidate fanned out
  between them. Dashed edges are being simulated, the heavy edge is the winner,
  a red dashed edge is a leg that reverted in simulation.
- **In flight.** One dot travels the winning route for as long as the
  transaction is pending. It is the only moving element, because it is the only
  thing happening: one value crossing several pools in one transaction.
- **Settled.** Every leg of the winner turns solid green together.
- **Rolled back.** The failing leg turns red, the legs before it return to
  dashed, and the message says that nothing was executed.

## Deadline and minimum

`swap_exact_in` takes no deadline. What bounds a signed route is the
transaction's own time bounds, set to three minutes, so a route that sat unsigned
in a wallet expires at the network layer instead of settling against a market
that has moved on.

Inside the call, the only protection is `min_out`: the quote the user saw minus
their slippage tolerance, on the final output only, exactly as for a direct
swap. See
[Slippage & Safety](/docs/protocol/slippage-and-safety).

## Testing locally

Open the swap page with `?routing=demo` or use the **Routing demo** strip under
the route panel. It adds Vault A (USDx / sUSDC) and Vault B (sUSDC / PYUSD) as
local pools priced with the same StableSwap math, next to the live pool.

- Small trades favour the direct route through the live pool; large trades
  favour the two-hop route through A and B, and the crossover is visible.
- With a multi-hop route selected, **fail at leg N** makes the next execution
  revert at that leg, which shows the all-or-nothing rollback.
- Demo routes walk through the same phases as a real transaction but nothing is
  signed or sent, and every screen says so.
